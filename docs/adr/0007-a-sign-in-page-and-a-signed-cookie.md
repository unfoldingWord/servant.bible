# ADR 0007: A sign-in page and a signed cookie in front of the page

- **Status:** Accepted
- **Date:** 2026-11-01
- **Deciders:** Ian Lindsley
- **Task:** Issue #39
- **Amends:** [ADR 0006](0006-the-page-behind-a-shared-password.md), decisions
  2 and 3; [ADR 0003](0003-one-router-worker-at-the-apex.md), decision 7
- **Depends on:** [ADR 0002](0002-url-naming-convention.md),
  [ADR 0006](0006-the-page-behind-a-shared-password.md)

## Context

ADR 0006 put the page at `/` and the HTML view of `/mcp` behind one shared
username and password, by HTTP Basic authentication, chosen because it needs
no form, no session, and no cookie. The cost is the browser's own login box:
it looks like an error dialog, it cannot be styled, and it reappears in every
new browser session. With the page itself live (#9, v0.6.0) and looking the
part, the vision owner asked on 2026-11-01 for a normal sign-in page instead.

What the gate protects, and what it must leave alone, does not change. ADR
0006 decision 1 stands: only the page is gated, and nothing a program calls
sees a credential check. This record changes how a person presents the
shared credential, and what the router has to hold to remember that they did.

## Decision

1. **The gate's front door is a sign-in page**, in the site's own design,
   generated by the same build step as the page so it shares the stylesheet.
   It is served at `GET /sign-in`, and it is the body of every `401` the gate
   answers to `GET` or `HEAD /` and to the HTML view of `/mcp`. That `401`
   carries no `WWW-Authenticate` header, so a browser never shows its own
   dialog. The status stays `401` so a monitor or `curl` can still tell a
   signed-out answer from the page without reading the body.
2. **`POST /sign-in`** takes `username` and `password` as a form
   (`application/x-www-form-urlencoded`). When they match the shared
   credential, compared in constant time as before, the router answers `303`
   to `/` with the cookie of decision 3. When they do not, it answers `401`
   with the sign-in page in its "did not match" form, and no cookie. A body
   over 4 KB answers `413` and any other content type `415`, before the
   credential is looked at. **`POST /sign-out`** clears the cookie and
   answers `303` to `/`; the page's nav carries that form. Any other method
   on these two paths answers `405`.
3. **The cookie is `servant_bible_page`**: `HttpOnly`, `Secure`,
   `SameSite=Lax`, `Path=/`, `Max-Age=2592000` (30 days). Its value is
   `<expiry>.<signature>`: the expiry as Unix seconds, and the base64url
   HMAC-SHA256, under a third secret `PAGE_COOKIE_SECRET`, of the expiry
   **and the credential**, `"<expiry>\n<username>:<password>"`. Binding the
   signature to the credential means rotating the password signs every
   browser out at once, without rotating the key. The router verifies in
   constant time and refuses a token that is expired, malformed, signed under
   another key, or signed for another credential.
4. **The router holds three secrets**, not two: `PAGE_USERNAME`,
   `PAGE_PASSWORD`, and `PAGE_COOKIE_SECRET`. Each deploy workflow sets them
   from the GitHub repository secrets `PAGE_COOKIE_SECRET_STAGING` and
   `PAGE_COOKIE_SECRET_PRODUCTION`, beside the four of ADR 0006, and refuses
   to deploy when any is empty. None is ever in `wrangler.toml`, in the
   repository, or set by hand. ADR 0003 decision 7 now reads: the router
   holds the page credential and the cookie key, and never a credential for
   any server.
5. **Basic authentication remains accepted** as a second way to present the
   same credential, for `curl` and the verification scripts: a request that
   already carries a correct `Authorization: Basic` header gets the page, and
   no cookie is set. It is no longer offered to browsers (decision 1).
6. **The cookie never reaches a backend.** The forwarder removes
   `servant_bible_page` from the `Cookie` header of every server call, the
   way ADR 0006 decision 3 keeps the credential from being sent upstream. Any
   other cookie the caller sends passes through as before.
7. **The gate still fails closed.** If any of the three secrets is missing,
   `/`, the HTML view of `/mcp`, `/sign-in`, and `/sign-out` answer `503` with
   a short JSON body and the router logs which secret is absent, never its
   value. The open addresses are unaffected.
8. **Nothing else changes.** `/mcp.json`, `/servers.schema.json`, `/health`,
   and every `/org/...` and `/s/...` address answer exactly as before, cookie
   or not. Everything the gate answers carries
   `Cache-Control: private, no-store`. The gate is still temporary by intent
   (ADR 0006, decision 7): removing it is one pull request that deletes the
   check, the three secrets, and the sign-in page.

## Consequences

- A browser at `servant.bible/` sees a sign-in page in the site's design,
  enters the shared credential once, and keeps the page for 30 days or until
  it signs out or the password is rotated. `curl -u` still works.
- A shared password behind a form is as guessable as it was behind Basic
  authentication, and the form makes guessing easier to script. A rate limit
  on `POST /sign-in` is a Cloudflare WAF rule, configured outside this
  repository, and is a follow-up issue, not part of this change.
- Login CSRF is moot with a shared credential; sign-out CSRF is blocked by
  `SameSite=Lax`, which keeps the cookie off a cross-site `POST`.
- Rotating the password now needs no cookie-key rotation; rotating the cookie
  key alone also signs everyone out. Both are a change to the repository
  secrets and a deploy.
- `wrangler dev` needs three values in `.dev.vars`; without all three the
  local page answers `503`, the same as a deployment missing a secret.
- Per-person access is still the separate decision ADR 0006 named: Cloudflare
  Access with a one-time code, configured outside this repository.
